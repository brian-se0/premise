## 2026-10-06 — Selective formal method

The owner asked for a maximally mathematical approach to the exam, limited to what helps students, and adopted the direction Claude and GPT-6 Pro agreed in two rounds (`reviews/2026-10-06-formal-method.md`): **systematic reading with selective formal checks** (`METHOD.md`). Every task starts from what it asks; evaluation tasks map evidence, claim and claimed connection; three kits (logic, quantity, evidence) switch on by meaning, and written answers stay in plain English. Order: the method and an audit of the published keys now; an optional, display-only `form` line per task (exercise schema 4) written into the draft batch before its key check; the grading check next, on frozen payloads with no form lines and the current taxonomy; then the tags `negation-error`, `quantifier-error`, `rate-vs-count` and `unit-of-analysis` with a grading recheck, then a stateless drill trial compared with form lines alone. **Why:** formal logic decides a minority of argument questions and most turn on evidence, where symbols cost time; this order keeps the grading check valid. **Rules out:** translating whole arguments into symbols, requiring notation for credit on argument or passage tasks, a mandatory basics course, and form lines or new tags entering grading payloads before a grading check covers them.

## 2026-10-05 — Import preserves historical text but enforces live lifecycle boundaries

Import accepts an old saved reply longer than the current 200,000-character save limit, while new replies still meet that limit. It refuses a draft in an ended session, a submitted or discarded answer over 2,000 characters, empty IDs, and session or request IDs that are not canonical lower-case UUIDs. Draft and skipped answers can exceed the submission limit and retain their text. An ended session may still contain submitted answers and unopened entries. Storage schema v1 and export schema 1 are unchanged. **Why:** backups from the live release must remain restorable, while inconsistent lifecycle state and IDs used in routes must not enter storage. **Rules out:** imposing a new save-time text cap retroactively on backups, truncating old data, or treating an ended session as proof that all its entries were opened.

## 2026-10-05 — Parser v4 recognizes bounded feedback headings consistently

Parser v4 uses one bounded heading recognizer for gaps, row boundaries and heading-score contradictions, including combined Markdown wrappers, paired outer table pipes, protocol whitespace after list markers, and list and quote markers in any order. A heading with marks outside its pipe pair is a boundary only; an unquoted, unfenced nested list heading is also a boundary, still counts toward its row's headings, and cannot start feedback. Quoted, fenced, tilde-wrapped and separator-less headings are boundaries that do not count toward their own rows. The heading-score check replaces emphasis and code marks with spaces, except between two digits, before removing an optional `Score` label and comparing with the unchanged score block. A backtick fence opener cannot have a backtick in its info string, so inline code on a list line does not open a fence. The narrow rule for these corrections is that a line may become a boundary, gain a heading-score check, or lose the right to start feedback, but may not newly start feedback; no previously read score changes. Saved v2 requests keep the legacy reader and their prompt bytes; prompt v4, score block grammar v2, score values, row statuses and choice options are unchanged. Confirmed feedback ranges remain stored; an unconfirmed parser-v3 reply must be read again before confirmation. **Why:** the independent Claude and GPT-6 Pro reviews of PR #3 found that inconsistent heading cleanup could attach I02's explanation to I01, and formatted contradictory scores could evade the attribution guard. **Rules out:** changing the score parser or retroactively rewriting stored grading feedback under an existing parser version.

## 2026-10-05 — Confirmation, counters and repairs respect the observed state

Parsed confirmation requires the answer, snapshot hash and exact reply text shown in its preview, compared to stored values inside the grading transaction. A counter increment stops before reaching `Number.MAX_SAFE_INTEGER`, so every saved state remains importable. A fresh success repairs a miss only when it began after the miss's earliest grading that showed a miss, including superseded gradings, while the later-submission and different-session rules remain. **Why:** replace-import can preserve IDs and text length while changing a reply, the previous counter guard allowed an unimportable terminal value, and deferred grading or a later downward correction can make an earlier success appear to repair a miss the student had not yet seen. **Rules out:** using a reply ID or matching length as proof of preview identity, suggesting export restores counter capacity, or clearing a miss from practice that predates its correction.

## 2026-10-04 — Draft writes bind to their saved text and session

Save, submit and skip now compare the editor's last accepted draft text and revision, fixed attempt identity, and original session entry inside the same transaction as the write. A missing or repointed session is stale. A repeated submission with identical text is idempotent only for the same attempt identity and session. The editor retains its local text and warns if a replacement backup removes or rewinds that session or attempt. Storage schema v1 and export schema 1 are unchanged. **Why:** a replace-import can reuse an attempt id and revision while changing its answer or identity, so revision alone cannot prevent a stale tab from overwriting or submitting the replacement. **Rules out:** accepting a restored id and revision as proof that a draft still belongs to the open editor.

## 2026-10-04 — Prompt v4 and parser v3 after the Opus review

Prompt v4 tells the chatbot to place every item's feedback inside one request-bound section, shows the actual row headings in that section, and asks for the score block directly afterward. Parser v3 requires the saved prompt version at every call site; for bounded feedback it refuses attribution when fence structure is uncertain or a heading's score contradicts the score block, while accepting unambiguous formatting around markers and headings. Every parsed grade must resolve to a saved reply read by the current parser and pass the confirmation-time reparse. The exact v2 and v3 prompt renderers remain available for saved requests; the score block grammar stays v2, and storage schema v1 and export schema 1 do not change. **Why:** the independent Opus 5.5 Max review (`reviews/2026-10-04-security-hardening.md`) found silent legacy fallback, cross-row feedback after malformed fences, ambiguous prompt instructions, and a fail-open parsed-grade precondition. **Rules out:** changing the wording or reply-reading behavior under an existing version, or trusting a parsed grade without a matching saved reply.

## 2026-10-04 — Prompt v3 and parser v2 bind feedback to its request
New grading prompts put the chatbot's per-row explanation between `BEGIN FEEDBACK request=<uuid>` and `END FEEDBACK`, immediately before the unchanged `BEGIN SCORES v2` block. Parser v2 associates feedback with a score only when one complete, request-matching feedback region belongs to the selected block; otherwise it keeps the score and leaves feedback unmatched. Existing v2 requests retain their exact prompt and legacy feedback reading, and stored replies remain readable. `promptVersion` and `parserVersion` already exist in storage, so schema v1 and export schema 1 do not change. **Why:** an ordinary chatbot quotation of an answer containing `I01:` could otherwise be mistaken for its explanation. **Rules out:** guessing feedback from unbounded prose for new requests.

## 2026-10-04 — M2 security and integrity follow-up
After the Opus 5.5 Max review and current-main reproductions, the M2 loop is hardened in place. An unfinished session may end when its next task is unavailable; submitted answers remain reachable for grading, and unopened tasks return to planning. Opening Today work rechecks the card due date, while Library may offer an early review. Skip checks the draft revision, and a live editor stops claiming "Saved" after another tab changes its draft. Every explicitly read, bounded chatbot reply is stored before grading and manual/self grades select their reply explicitly. Parsed grades from parser v2 are checked against the stored reply in the confirming transaction. Each unresolved miss has its own repair identity; only a strictly later fresh success in a different session can repair it. Import rejects inherited-key scheduler/setting lookups, malformed or non-finite scheduler data, unusable cards, unsafe counters, oversized replies and grading prompts that differ from their frozen inputs. Counter increments fail before JavaScript would round them. These checks keep schema v1 and export schema 1 unchanged. **Why:** the audit found ways to lose drafts or reply provenance, strand a session, mis-schedule a review, or import data that later breaks grading and export. **Rules out:** treating a backup file, a stale tab or a copied prompt as trusted merely because its surface shape is valid.

## 2026-10-04 — Review order, out-of-order grades and scheduler configurations
Each review log gets `seq`, the highest stored seq plus one, assigned inside the applying transaction; "latest review" for undo and correction is the highest seq among a task's active reviews, and `appliedAt` is display-only. `reviewedAt` is always the attempt's submission time; a grade confirmed after a later review of the same task is applied to the current card with the scheduler run at the later of the submission time and the card's last review, recorded as `cardAfter.last_review`, with no replay. New reviews always use the current scheduler; configurations for scheduler versions this build doesn't know are kept in a `schedulerConfigs` table and re-exported, import refuses a missing configuration or a known version defined differently, and `cardBefore` keeps its own scheduler version so undo is exact. **Why:** M2-1, M2-11 and M2-12: caller clocks repeat or run backwards, the clamped time overwrote when the student answered, and imported configurations were lost. **Rules out:** ordering reviews by time or id; history replay.

## 2026-10-04 — Operation contracts tightened after the M2 review
Draft saves check and increment the attempt revision; a repeated submission succeeds only with identical text. `openEntry` rechecks eligibility in its transaction (another uncoached draft of the task, suspended, a submitted attempt awaiting a grade, `notBefore`) and returns the competing draft rather than creating a second one; coached retries are the only exception. `confirmRows` and `discardRows` refuse repeated attempts and rows outside the request, and `abandonRequest` checks the revisions the student saw. Correction applies only to accepted rows with a valid score, keeps the reply and feedback provenance, and leaves `taskStates` alone; only confirmation sets `notBefore`. A pasted reply with no usable scores is stored (`saveReply`) and grades entered by hand can link to it. Import requires canonical UTC `toISOString()` timestamps, validates settings by key and refuses unknown keys, measures size in bytes before reading, and treats `disclosureSeen` and `persistGranted` as device-local (not exported, kept on replace). The integrity checker adds ownership, range, lifecycle, card-chain and time checks. **Why:** M2-3, M2-5, M2-6, M2-10, M2-13, M2-14, M2-16, M2-17 and M2-23. **Rules out:** a separate locking system; anti-tampering for backups.

## 2026-10-04 — Planner v1 after the M2 review
Today's session (four tasks) reserves one slot for a fresh repair whenever an open miss has one; then due reviews (earliest first; in final-weeks mode capped per day, open misses first); then fresh repairs for other misses; then new tasks (unseen arguments first, focus matches first, easier first). A missed task is repeated only after its fresh repair in the same session; if both don't fit, the repeat waits. A fresh repair is a task on an exercise the student has never seen, with the missed task's skill and a shared likely error; when none exists the miss is marked as having no fresh check and the results page says so, and new tasks are never presented as repairs. A miss is repaired only by an uncoached, full-credit attempt on an unseen stimulus. Final-weeks mode applies its difficulty floor to due reviews too; a fresh repair is the one stated exception. The conclusion policy applies to due and new tasks alike, coached attempts are not evidence, and the Library still offers every task. Today and New only never offer a task from an exercise already shown that day unless every task shown from it and the new task are due reviews; Library sessions are exempt but count as shown. **Why:** the M2 review (M2-18 to M2-22) found due-first planning removed repair under normal load, "different exercise" stood in for "fresh stimulus", and the final-weeks, conclusion and spacing rules applied only to new tasks or one session. **Supersedes:** the planner sentences in "M2 vertical slice as built". **Rules out:** adaptive weighting or tuning before M3 data.

## 2026-10-04 — Parser v1: incomplete candidates and explicit trimming
An incomplete score-block candidate consumes all text up to the line that ends it: the next `BEGIN SCORES` line, an echoed `=== END OF ITEMS ===` line, or the end of the reply; its displayed range still ends at its last row. Feedback after an unterminated candidate is never attributed to a later block, so that block's feedback is left unmatched rather than guessed. Trimming removes JavaScript whitespace except U+FEFF, and zero-width characters are never trimmed, so `2<U+FEFF>/2` is invalid rather than repaired. `PARSER_VERSION` stays 1 because no reply had been stored under the earlier reading. **Why:** M2-8 and M2-9. Recorded in `GRADING_PROTOCOL.md` §9a.

## 2026-10-04 — Grading state model
Gradings are revisions with their own ids; each attempt has one current grading and at most one active review, and each review log stores the card state before it so the latest review can be undone exactly. "Needs review" is not terminal: a request stays open until every row is accepted or discarded. Every grading change is an operation with an id and an expected attempt revision, run in one IndexedDB transaction. Submitted attempts are frozen and belong to one request. **Why:** v0.2 could not store a correction's history, closed requests that still needed action, and treated "same score" as idempotency. **Rules out:** a history-replay engine, post-confirm rating changes in v1.

## 2026-10-04 — Scheduler fsrs-1 and next-day eligibility
ts-fsrs with retention 0.9, maximum interval 365 days, no fuzz, no short-term steps, default weights copied into the repo. A confirmed task is not offered again before the next local day. Review time stays the submission time. **Why:** delayed grading must not let a student be "reviewed" on an answer they just read. The rating policy is reassessed with M3 usage, not M0. **Supersedes:** "calibrated with pilot data" in Rating policy v1.

## 2026-10-04 — Copy-and-paste grading with a score block

## 2026-10-04 — Free-response reasoning trainer
Students write conclusions, assumptions, flaws and main points for original or public-domain arguments and passages, graded against reference answers and rubrics. **Why:** trains producing answers rather than recognizing them, which official multiple-choice practice does not, and AI grades written answers against a reference far more reliably than it writes multiple-choice questions. **Rules out:** a multiple-choice question bank.

## 2026-10-04 — No official content, no test branding
